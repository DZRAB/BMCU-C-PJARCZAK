# BMCU-C 编译指南

本指南说明如何在本仓库编译 BMCU 固件。本工程**不使用 MounRiver Studio**，而是基于 **PlatformIO + 社区 CH32V 平台**（`Community-PIO-CH32V`）构建。所有编译变体都定义在 `platformio.ini` 中。

---

## 一、环境准备

只需准备好以下基础工具，编译器和 SDK 由 PlatformIO 首次编译时**自动下载**：

| 依赖 | 作用 | 是否自动安装 |
|------|------|--------------|
| **Python 3** | PlatformIO 运行环境 | 需自行安装 |
| **git** | 首次编译需从 GitHub 克隆 `Community-PIO-CH32V` 平台源码 | 需自行安装 |
| **PlatformIO (pio)** | 构建系统 | 需自行安装：`pip install platformio` |
| **联网** | 拉取平台包 + RISC-V GCC 工具链 + WCH noneos-sdk | 需联网 |
| **RISC-V GCC / WCH noneos-sdk** | 实际编译器 | ✅ 自动下载 |

> **Windows 用户提示**：在 **Git Bash / PowerShell / CMD** 中执行命令均可，只要 `pio` 和 `git` 在 PATH 中。若使用 **VSCode 的 PlatformIO 插件**，它自带 Python 和 pio，打开工程后直接点 Build 即可（仍需系统安装 git）。

安装验证：

```bash
python --version    # 或 python3 --version
git --version
pio --version
```

## 二、编译单个固件（最常用）

进入工程根目录，用 `-e` 指定一个构建变体：

```bash
pio run -e moj
```

- `moj`：单 BMCU（SOLO）固件，回抽 9.5 cm（`BAMBU_BUS_AMS_NUM=0`、`AMS_RETRACT_LEN=0.095f`）。
- 其他变体把 `moj` 换成对应的 `[env:xxx]` 名称即可，例如 `pio run -e ams_a_030`、`pio run -e ams_d_050`。

### 变体命名规则

`platformio.ini` 中每个 `[env:xxx]` 就是一个变体：

- **`moj`**：单模块（SOLO）固件，回抽长度固定 0.095f（9.5 cm）。
- **`ams_a_xxx` ~ `ams_d_xxx`**：`AMS_A`~`AMS_D` 四个槽位，后缀数字为回抽长度（米）。**注意**：这些环境仅列举常用回抽长度（0.10~0.90 米），并非穷举；回抽长度可自定义，AMS_A~D 实际支持 **0.10~2.00 米、步长 5cm（共 39 档）**，通过 `fw` 环境的环境变量 `AMS_RETRACT_LEN` 或 `build_one.sh` 的 `<RETRACT>` 参数指定（见下文）。示例：
  - `ams_a_030` → `BAMBU_BUS_AMS_NUM=0`，回抽 `0.30f`（30 cm）
  - `ams_b_010` → `BAMBU_BUS_AMS_NUM=1`，回抽 `0.10f`（10 cm）
  - …以此类推，内置列举档位含：`010 020 025 030 035 040 045 050 055 060 065 070 075 080 085 090`（单位：米）
- **`fw`**：特殊环境，**从环境变量读取编译参数**，用于和一键脚本配合批量构建（见下文）。

> 注：单变体编译（如 `moj`、`ams_a_030`）只设置了槽位和回抽长度，**未开启** AUTOLOAD / RGB / P1S / SOFT_LOAD 等可选功能。需要这些功能请用 `fw` 环境手动传参。

### 单固件归档到 single_build/（build_one.sh）

上面 `pio run -e moj` 的产物只是 `.pio/build/<env>/firmware.bin`，**不分目录、不按功能命名**。若希望**单独编译一个固件、也像批量脚本那样分目录并命名成 `solo_0.095f.bin` / `ams_a_0.30f.bin`**，用封装脚本 `build_one.sh`（底层仍是 `fw` 环境传参 + 复制归档，命名规则与 `build_all_firmwares_softload.sh` 完全一致）。

> 注意：单固件产物放在独立的 **`single_build/`** 目录（**不是**批量专用的 `firmwares/`），两者都被 `.gitignore` 忽略、不入库；`single_build/` 用于单独补编，避免与全量构建产物混淆。

```bash
bash build_one.sh standard 1 1 SOLO     # AUTOLOAD=1(双开关)：single_build/.../SOLO/solo_2.00f_auto.bin  （忽略回抽长度，自动回抽）
bash build_one.sh softload 1 0 A 0.30   # AUTOLOAD=1(双开关)：single_build/.../AMS_A/ams_a_2.00f_auto.bin （0.30 被忽略）
bash build_one.sh p1s 0 1 D 0.80        # NO_AUTOLOAD=0(单开关)：single_build/.../AMS_D/ams_d_0.80f.bin （仍需选回抽长度）
bash build_one.sh standard 1 1 A 0.30 0 # AUTOLOAD=1(双开关)+AUTO_RETRACT=0：ams_a_0.30f.bin （固定回抽长度模式，0.30 生效）
```

参数顺序：`<MODE> <AUTOLOAD> <RGB> <SLOT> <RETRACT> [AUTO_RETRACT]`，其中 `MODE` 为 `standard|p1s|softload`，`SLOT` 为 `SOLO|A|B|C|D`，`RETRACT` 为回抽长度（米，SOLO 可省略默认 `0.095`；**AUTOLOAD=1（双开关）且未给第 6 参数（默认 1=自动回抽）时忽略此参数**，回抽由 S2 自动判定，文件名加 `_auto` 后缀）；第 6 参数 `AUTO_RETRACT` 省略时默认 `1`（自动回抽），双开关板设 `0` 即固定回抽长度模式（此时 `RETRACT` 生效、文件名不带 `_auto`）。该脚本**不会删除**现有 `single_build/`，只把单个固件放入对应位置，便于单独补编后并入 Releases 包。

## 三、用 `fw` 环境手动传参（完全自定义）

`[env:fw]` 从环境变量读取全部编译宏，可生成脚本未覆盖的组合（例如 `soft_load`）：

```bash
BAMBU_BUS_AMS_NUM=0 \
AMS_RETRACT_LEN=0.095f \
BMCU_DM_TWO_MICROSWITCH=1 \
BMCU_ONLINE_LED_FILAMENT_RGB=1 \
DBMCU_P1S=0 \
BMCU_SOFT_LOAD=0 \
pio run -e fw
```

各宏含义：

| 宏 | 取值 | 含义 |
|----|------|------|
| `BAMBU_BUS_AMS_NUM` | `0`~`3` | AMS 槽位编号，对应 A~D |
| `AMS_RETRACT_LEN` | 浮点（米） | filament 回抽长度，如 `0.095f` = 9.5 cm |
| `BMCU_DM_TWO_MICROSWITCH` | `0`/`1` | 双微动开关板 + AUTOLOAD（1 = 开启）；`0` = 单开关板 |
| `BMCU_DM_AUTO_RETRACT` | `0`/`1`（默认随 `BMCU_DM_TWO_MICROSWITCH` 派生：双开关=1 开、单开关=0 关） | 自动回抽开关（仅双开关有效）。`1`=用 S2 自动判定料根；`0`=双开关改用固定回抽长度、须编译全长度矩阵。两种回抽方式的区别见 [`BMCU使用指南.md`](./BMCU使用指南.md) 2.5 节 |
| `BMCU_ONLINE_LED_FILAMENT_RGB` | `0`/`1` | 装入后 ONLINE LED 显示 filament RGB（1 = 开启） |
| `DBMCU_P1S` | `0`/`1` | P1S 模式（1 = 开启，高力加载） |
| `BMCU_SOFT_LOAD` | `0`/`1` | soft_load(A1) 软加载模式（1 = 开启） |
| `SIM_AHB_PROBE_ENABLE` | 文件内开关（`src/sim_aht20.h`） | 温湿度探测模拟开关（调试用，**非编译宏**）：`1`=开启，在每次响应打印机查询时自增温湿度使显示随查询周期跳变以便测量打印机拉取周期；`0`=关闭（函数为空操作）。**直接改 `src/sim_aht20.h` 顶部的 `#define SIM_AHB_PROBE_ENABLE 1/0` 后重新编译即可**，对所有编译方式通用，无需命令行或平台传参 |

> **关于 `BMCU_DM_AUTO_RETRACT=0`（双开关固定回抽长度模式）**：默认双开关=1（开自动回抽）。该项只在“双开关硬件却想要固定回抽长度”时才编译（如 S2 不可靠 / 个人偏好）。触发方式：`build_one.sh` 第 6 参数 `AUTO_RETRACT=0`、`build_all_firmwares_fast.py` 环境变量 `AUTO_RETRACT=0`，触发后双开关也出 39 档固定回抽长度矩阵（总固件数从默认 972 升到 1884）。`build_all_firmwares_softload.sh` 固定只出双开关自动回抽版（不读该开关）。两种回抽方式的区别见 [`BMCU使用指南.md`](./BMCU使用指南.md) 2.5 节。

> **关于 `soft_load(A1)`**：`build_all_firmwares_softload.sh` 已内置 `soft_load(A1)` 模式（编译参数 `DBMCU_P1S=0` + `BMCU_SOFT_LOAD=1`），可一次性生成全部三种模式的固件。如需脚本未覆盖的组合，可用 `fw` 环境单独编译（见第三节）。

## 四、一键编译全部固件

`build_all_firmwares_softload.sh` 会遍历 **打印机模式 × {双开关自动回抽(AUTOLOAD) , 单开关(NO_AUTOLOAD)} × RGB × 槽位** 全组合（含 `soft_load(A1)` 模式），生成完整的 `firmwares/` 目录树（含 `manifest.txt` 校验清单）。注意：**双开关走自动回抽，每槽只产 1 个 `xxx_2.00f_auto.bin`，不遍历回抽长度；只有单开关(NO_AUTOLOAD) 才遍历全部回抽长度矩阵**。该脚本无固定长度开关，双开关固定长度矩阵请用 `build_all_firmwares_fast.py` + `AUTO_RETRACT=0`（见下文）。

```bash
bash build_all_firmwares_softload.sh
```

脚本行为说明：

1. 开头执行 `rm -rf firmwares` 后重建——**会删除现有 `firmwares/` 目录**再重新生成。
2. 生成的目录结构：
   ```
   firmwares/
   ├── README.md                       (由 which_to_choose_mode.txt 改名)
   ├── standard(A1)/                    (DBMCU_P1S=0)
   │   └── AUTOLOAD/ / NO_AUTOLOAD/
   │       └── FILAMENT_RGB_ON/ / FILAMENT_RGB_OFF/
   │           └── SOLO/ AMS_A/ AMS_B/ AMS_C/ AMS_D/
   ├── high_force_load(P1S)/            (DBMCU_P1S=1)
   │   └── ... (同上结构)
   └── soft_load(A1)/                   (DBMCU_P1S=0 + BMCU_SOFT_LOAD=1)
       └── ... (同上结构)
   ```
3. 每个子目录里的 `README.md` 由根目录对应的 `which_to_choose_*.txt` 复制并重命名而来（mode→顶层/模式目录，autoload→AUTOLOAD/NO_AUTOLOAD，filament_rgb→RGB 目录，slots→最里层）。
4. 末尾用 Python 生成 `firmwares/manifest.txt`（每行：`SHA256 CRC32 大小 相对路径`），用于校验固件完整性。

> **注意**：`firmwares/` 下各层的 `README.md` 均由脚本从根目录 `which_to_choose_*.txt` 复制改名自动生成（并非手动添加），`which_to_choose_*.txt` 源文件本身仍保留在仓库根目录供脚本读取。`firmwares/` 已被 `.gitignore` 忽略、不受 git 跟踪，误删只能重新运行脚本生成（或从 Releases 下载）。

**编译后会生成什么：**

- 编译矩阵：3 种模式 × {AUTOLOAD(双开关,自动回抽,每槽 1 个) , NO_AUTOLOAD(单开关,SOLO×1 + AMS_A~D×39)} × FILAMENT_RGB_ON/OFF = **972 个 `.bin`**（双开关自动回抽 30 + 单开关 942）。
  - 若用 `build_all_firmwares_fast.py` 并设 `AUTO_RETRACT=0`，双开关也出 39 档固定回抽长度矩阵，总数升到 **1884 个**（双开关 942 + 单开关 942）。
  - 双开关（AUTOLOAD）：每槽仅 1 个 `xxx_2.00f_auto.bin`，回抽长度由 S2 自动判定，`2.00` 仅作安全上限，无需选择回抽长度。
  - 单开关（NO_AUTOLOAD）：SOLO 固定 9.5cm；AMS_A~D 每槽 0.10~2.00 米、步长 5cm 共 39 档。
- 目录结构：`standard(A1)/`、`high_force_load(P1S)/`、`soft_load(A1)/` 三个模式目录，每个下再分 `AUTOLOAD/NO_AUTOLOAD` → `FILAMENT_RGB_ON/OFF` → `SOLO/AMS_A~D/`，最里层为 `solo_2.00f_auto.bin` / `ams_a_2.00f_auto.bin`（双开关）或 `solo_0.095f.bin` / `ams_a_0.30f.bin`（单开关）等。
- 文档文件：每个层级仅带 `README.md`（=对应选型指南中文版），三种模式格式统一。
- 校验文件：`firmwares/manifest.txt`。

> **耗时提醒**：脚本对 `fw` 环境执行约 972 次 `pio run`（单开关 942 次 + 双开关自动回抽 30 次），且每次编译宏不同会触发全量重编；首次还需联网下载工具链。整体耗时很长（实测数小时），建议在后台运行，不要中途打断。

### 高速批量编译（build_all_firmwares_fast.py）

仓库提供 `build_all_firmwares_fast.py`，在**保持与 `build_all_firmwares_softload.sh` 完全一致的输出目录结构、文件命名与 `manifest.txt` 校验清单**的前提下，大幅缩短编译时间（约 972 个固件只需几分钟，常规脚本需数小时）。

```bash
python build_all_firmwares_fast.py              # 默认：双开关自动回抽，共 972 个
AUTO_RETRACT=0 python build_all_firmwares_fast.py   # 双开关也出固定回抽长度矩阵，共 1884 个
```

**原理简介：**

- **工具链参数提取**：`pio run -e moj -v` 提取编译/链接命令行并缓存（首次提取后，只要 `platformio.ini` 未改动即复用，跳过提取步骤）。
- **共享编译**：不受变体宏影响的 `.o`（Framework SDK + 不变用户源）只编译一次；受宏影响的源按「模式组合」编译并缓存复用，避免每个固件全量重编。
- **回抽长度二进制修补**：`AMS_RETRACT_LEN` 仅作用于 `Motion_control`，故基础固件以占位符浮点 `123.456f` 编译，最终在 `.bin` 中将该浮点二进制替换为目标回抽长度，省去为每档回抽长度重编 `Motion_control.cpp`。（默认双开关自动回抽固件每槽仅 1 个，直接修补为 `2.00f` 安全上限；单开关 39 档仍逐档修补；设 `AUTO_RETRACT=0` 时双开关同样走 39 档逐档修补路径）

**运行报告：** 脚本结束会打印精准的分阶段计时（提取参数 / 预编译 `.o` / 链接与修补 / 总耗时）与具体固件数量（总数 / 成功 / 失败）。

**配置项（脚本顶部）与环境变量：**

| 变量 | 含义 |
|------|------|
| `AUTO_RETRACT`(环境变量，默认 `1`) | 仅对双开关(AUTOLOAD)生效。`1`=自动回抽（每槽 1 个 `_auto`，共 972）；`0`=双开关也按固定回抽长度矩阵编译（每槽 39 档，共 1884）。单开关(NO_AUTOLOAD) 不受此变量影响，始终走全长度矩阵 |
| `FAST_MODE` | `True`：二进制修补回抽长度（最快，默认）；`False`：每档回抽长度重编 `Motion_control.cpp`（输出与 `pio run -e fw` 字节级一致，但更慢） |
| `OUT_DIR` | 输出目录，默认 `firmwares` |
| `MAX_JOBS` / `LINK_JOBS` | 可通过环境变量覆盖并行编译线程数与最大并发链接数 |

> 说明：高速模式（默认）下，因 LTO 链接顺序/分区差异，生成的 `.bin` 与 `pio run -e fw` 存在字节级差异，但功能完全等价（已通过变体宏差异、回抽长度修补差异验证）。如需与 pio 字节级一致的产物，设 `FAST_MODE=False`。

**缓存目录 `.pio_parallel/`（自动生成，已被 `.gitignore` 忽略）：**

脚本运行时会创建 `.pio_parallel/` 存放中间产物，可放心删除（下次运行自动重建）：

- `verbose_cache.txt` — `pio run -e moj -v` 提取的工具链路径与编译/链接命令行；只要 `platformio.ini` 未改动即复用，跳过重新提取。
- `obj_cache/` — 预编译的 `.o` 文件（按「模式组合」分类缓存），二次运行命中缓存可跳过重复编译。

若改动了 `platformio.ini` 或工具链后结果异常，删除 `.pio_parallel/` 强制重建缓存即可。

## 五、编译产物位置

### 单变体编译

产物位于：

```
.pio/build/<env名>/firmware.bin
```

例如 `pio run -e moj` 的产物为 `.pio/build/moj/firmware.bin`。同目录附带：

- `firmware.elf` — 带调试信息的可执行文件
- `firmware.map` — 内存映射（查看 RAM / Flash 占用）
- 其它中间产物视平台而定

> 若希望单固件也分目录并命名成 `solo_0.095f.bin` / `ams_a_0.30f.bin`，用 `build_one.sh`（见上文「单固件归档到 single_build/」），产物位于 `single_build/`，命名规则与一键脚本完全一致。

### 一键脚本编译

产物按模式/槽位/回抽长度分类放在 `firmwares/` 目录树中，例如：

```
firmwares/standard(A1)/AUTOLOAD/FILAMENT_RGB_ON/SOLO/solo_2.00f_auto.bin
firmwares/high_force_load(P1S)/AUTOLOAD/FILAMENT_RGB_ON/AMS_A/ams_a_2.00f_auto.bin
```

## 六、刷写固件

> ⚠️ **注意**：本仓库（BMCU-C）的二次开发固件**不支持 BMCU Flasher**。BMCU Flasher 仅适用于原作者原版固件，用它刷本仓库固件会失败。请用 **WCHISPTool**（WCH 官方 ISP 工具）烧录本仓库编译出的 `firmware.bin`。

### 方式一：WCHISPTool（推荐，无需调试器）

WCHISPTool 通过 CH32V203 芯片内置的**系统 bootloader** 烧录。步骤：

1. 让芯片进入系统 bootloader：将 **BOOT0 拉高、BOOT1 拉低**，然后上电/复位。
2. 连接电脑（二选一）：
   - **USB 方式**：接芯片的 USB D+/D-（CH32V203 系统 bootloader 自带 USB，WCHISPTool 直接识别）；
   - **串口方式**：通过 USB-TTL 适配器接系统 bootloader 对应的 USART（CH32V203 通常为 USART1，PA9/PA10）。
   - 具体 BOOT 引脚位置、USB/串口焊盘以你的 **BMCU 370C** 板实物为准（板子未引出时需接烧录测试点）。
3. 打开 WCHISPTool，选择芯片 **CH32V203**，载入编译产物 `firmware.bin`，点击「下载 / 烧录」。
4. 烧录完成后，将 **BOOT0 拉低** 恢复从 Flash 启动，复位上电即可运行。

### 方式二：PlatformIO + WCH-Link 调试器

若手头有 **WCH-Link** 调试器及驱动，也可直接烧录：

```bash
pio run -e moj -t upload
```

普通刷写推荐用 WCHISPTool，无需额外调试器。

## 七、常见问题

**Q：第一次编译卡很久？**
A：正常。PlatformIO 正在后台下载 CH32V 平台包和 RISC-V GCC 工具链（需联网）。下载完成后后续编译很快。

**Q：提示找不到 `pio`？**
A：确认已 `pip install platformio` 且安装路径在 PATH 中；或使用 VSCode PlatformIO 插件。

**Q：提示找不到 `git`？**
A：安装 git 并确保可全局调用，平台包通过 git 从 GitHub 克隆。

**Q：想恢复被脚本误删的 `firmwares/`？**
A：`firmwares/` 已被 `.gitignore` 忽略、不受 git 跟踪，无法用 git 恢复；重新运行 `bash build_all_firmwares_softload.sh` 重新生成，或从 Releases 下载对应固件。

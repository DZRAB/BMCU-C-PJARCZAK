# 为什么改一个编译参数就能编出不同固件？—— 构建系统设计讲解

> 面向没学过编程 / 刚接触嵌入式固件的读者。
> 读完这份文档，你会明白 BMCU 这个项目为什么能用同一份源码，
> 通过 `-D开关名=值` 这样一行参数，编译出上千种不同行为、却互不打架的固件。

---

## 0. 一句话先给结论

固件里**同一份 C/C++ 源码是"模板"**。在编译（把人读得懂的代码翻译成芯片能跑的机器码）
的那一刻，编译器可以根据你给的"开关"（编译期宏），决定：

- 把哪些代码**编进去**、哪些代码**整段扔掉不编**；
- 把某些数字（如回抽长度 `0.10` 米）直接**写死**进机器码。

因为"扔掉 / 写死"发生在**编译前**，所以每个固件都是从同一份模板"裁"出来的、
彼此独立的成品——它们自然不会互相干扰。

下面把这背后的几个机制，从最基础讲起。

---

## 1. 基础概念：什么是"编译"，什么又是"编译参数"

### 1.1 从源码到固件

你写的 `.cpp` / `.h` 文件是**给人看的文本**。芯片只认二进制的机器指令。
中间的翻译过程叫**编译**（compile）：

```
源码 .cpp ──(编译器 g++)──► 目标文件 .o ──(链接器)──► 固件 .bin
```

- **编译**：把单个 `.cpp` 翻成 `.o`（机器码，但还没拼好）。
- **链接**：把一堆 `.o` + 系统库拼成最终的 `.bin`（能烧进芯片的文件）。

### 1.2 编译参数 `-D` 就是"全局开关"

`-D名字=值` 是编译器的一个开关，意思是"在编译开始之前，先定义一个宏"。
它等价于在所有源码最前面加一行：

```c
#define 名字 值
```

举例：

```
pio run -e fw -D BMCU_DM_TWO_MICROSWITCH=1
```

效果等同源码里出现：

```c
#define BMCU_DM_TWO_MICROSWITCH 1
```

这个宏**只存在于编译那一刻**，不会写进任何源码文件，也不会影响别的固件。

> 类比：同一本菜谱（源码），`-D辣度=高` 是"这次做辣的"，
> `-D辣度=低` 是"这次做不辣的"。菜谱没改，只是出锅的菜不同。

---

## 2. 核心魔法 ①：用 `#ifdef` 让代码"按需存在"

C/C++ 提供"条件编译"指令：只有宏被定义了，那段代码才参与编译。

### 2.1 看真实代码

`src/Motion_control.cpp` 里有一段（约 2693 行）：

```cpp
#if defined(BMCU_ONLINE_LED_FILAMENT_RGB) && (BMCU_ONLINE_LED_FILAMENT_RGB + 0)
    auto &Acol = ams[motion_control_ams_num];
#endif
```

含义：**只有当 `BMCU_ONLINE_LED_FILAMENT_RGB` 被定义且为真时**，
`Acol` 这个变量才会被编译进去。

这就是为什么之前改 RGB 逻辑时踩过坑：宏关掉（OFF）时，`Acol` 根本不存在，
代码里不能再引用它——必须改用 `ams[motion_control_ams_num]`。

### 2.2 再看 TPU 专用固件的开关

`src/tpu_params.h` 末尾（145 行）：

```cpp
#ifdef BMCU_TPU_MODEL
// …… 仅"专用固件"才编进来的接口 ……
static inline const _tpu_param *tpu_param_selected(void) { ... }
#endif
```

含义：没定义 `BMCU_TPU_MODEL`（通用固件默认）时，这段"强制固定型号"的
代码**完全不编译**，固件行为退回 v3.2，零差异。

### 2.3 为什么"不出错"

关键点：条件编译是在**编译前**由预处理器裁切的。芯片拿到的 `.bin` 里：

- 双开关固件：根本没有"单开关"那段逻辑；
- RGB 关闭固件：根本没有 `Acol` 这个变量；
- 普通固件：根本没有 TPU 专用接口。

每个固件都是被"裁"干净的独立成品，**运行时不共享任何状态**，
所以再多型号组合也不会互相踩踏。

---

## 3. 核心魔法 ②：用宏把数字"写死"进机器码

有些参数不需要改变逻辑，只是数值不同，比如**回抽长度**。

`platformio.ini` 里：

```ini
build_flags =
  -DAMS_RETRACT_LEN=${sysenv.AMS_RETRACT_LEN}
```

源码里 `AMS_RETRACT_LEN` 直接当数字用（如 `0.95f`）。编译后，这个
浮点数被**直接写进机器码**，运行时不再需要读配置。

好处：
- 固件小巧、运行快（不用存表、不用查表）；
- 改长度不需要改源码，只改编译参数即可。

坏处（也是后续"加速编译"要解决的难点，见第 6 节）：
- 每换一个长度，就得重编一次 `Motion_control.cpp`。

---

## 4. 把开关集中管理：platformio.ini 的 `[env:xxx]`

### 4.1 每个 `[env:名字]` 就是一套"参数预设"

`platformio.ini` 不是脚本，而是**编译配置表**。每一段 `[env:xxx]` 是
一套参数组合。例如：

```ini
[env:base]
build_flags =
  -DSYSCLK_FREQ_144MHz_HSI=144000000
  ; 下面这些是被注释掉的开关，手动启用就编进对应功能
  ; -DBMCU_DM_TWO_MICROSWITCH=1
  ; -DBMCU_ONLINE_LED_FILAMENT_RGB=1
  ; -DBMCU_P1S=1
  ; -DBMCU_SOFT_LOAD=1
```

```ini
[env:fw]
extends = env:base
build_flags =
  ${env:base.build_flags}
  -DBMCU_DM_TWO_MICROSWITCH=${sysenv.BMCU_DM_TWO_MICROSWITCH}
  -DBMCU_ONLINE_LED_FILAMENT_RGB=${sysenv.BMCU_ONLINE_LED_FILAMENT_RGB}
  -DBAMBU_BUS_AMS_NUM=${sysenv.BAMBU_BUS_AMS_NUM}
  -DAMS_RETRACT_LEN=${sysenv.AMS_RETRACT_LEN}
```

- `extends = env:base`：先继承 base 的所有配置，再叠加自己的。
- `${sysenv.XXX}`：从**环境变量**读值。这样一键脚本就能用同一套 `[env:fw]`
  喂不同的环境变量，编出所有组合，而不用把每种组合都写死成一段 `[env:xxx]`。

### 4.2 为什么不全写成 `[env:ams_a_010]`…`[env:ams_d_090]`

你看到 `platformio.ini` 里列了一堆 `ams_a_010`、`ams_b_030`… 那只是
**常用回抽长度的人工快捷方式**（`pio run -e ams_a_030` 图方便）。
真正全量（39 档 × 4 槽 × 双/单开关 × RGB开关 × 3 种推力模式 = 上千个）走的是
`[env:fw]` + 环境变量，由 `build_all_firmwares_fast.py` 一次性跑完。

## 5. 组合爆炸：到底有多少种固件

维度拆解（来自 `build_all_firmwares_fast.py` 里的 `tasks` 生成逻辑）：

| 维度 | 取值 | 含义 |
|------|------|------|
| 开关类型 | 双 / 单 | `BMCU_DM_TWO_MICROSWITCH` |
| RGB 开关 | 开 / 关 | `BMCU_ONLINE_LED_FILAMENT_RGB` |
| 推力模式 | A1 / P1S / 软载 | `BMCU_P1S` / `BMCU_SOFT_LOAD` |
| AMS 槽位 | SOLO / A / B / C / D | `BAMBU_BUS_AMS_NUM` |
| 回抽长度 | 0.10 ~ 2.00 米（39 档） | `AMS_RETRACT_LEN` |

仅常规矩阵就有 **约 2 × 2 × 3 × 5 × 39 ≈ 2340 个**固件（单开关全矩阵时）。
再叠加 TPU 专用（6 个型号 × 上面的部分组合），总量更大。

如果**每个固件都从零完整编译**，按脚本头部注释，原本要**数小时**。

---

## 6. 怎么让上千个固件"又快又不出错"：构建脚本的设计

`build_all_firmwares_fast.py` 是真正的"批量编译大脑"。它把上面讲的原理
工程化，用三个关键技巧把数小时压到约 1 分钟。

### 6.1 技巧一：把源码按"受哪些宏影响"分类

脚本扫描每个 `.cpp`，递归看它（和它 `#include` 的头文件）引用了哪些变体宏，
分成三类（`scan_macros` 函数）：

- **INVARIANT（不变）**：完全不引用任何变体宏 → 编译**一次**即可，所有固件共用。
- **OTHER（模式相关）**：引用了开关类宏（如双/单开关、RGB、P1S）→ 按
  "模式组合"（dm×rgb×p1s×soft_load×ams_num）编译一次并缓存复用。
- **RETRACT（回抽相关）**：只引用 `AMS_RETRACT_LEN` → 特殊处理（见下）。

这样：绝大多数源码属于 INVARIANT，只编一次；真正"多变体"的只是少数几个文件。

### 6.2 技巧二：二进制修补回抽长度（最巧妙的一招）

回抽长度 `AMS_RETRACT_LEN` 只被 `Motion_control.cpp` 用到。如果每个长度都
重编它，39 档要重编 39 次。

脚本的做法：

1. 先用一个**占位符浮点** `123.456f` 编译基础固件；
2. 在最终 `.bin` 里，把 `123.456f` 的 4 字节二进制，直接**替换**成目标长度
   的 4 字节（如 `0.95f`）。

因为浮点在二进制里就是 4 个字节，`struct.pack("<f", 0.95)` 就能算出目标字节，
`bytearray.find / replace` 就能改。**完全不需要重编** `Motion_control.cpp`。

```python
base[pos:pos+4] = struct.pack("<f", float(retract_len.rstrip("f")))
```

> 这就是"编译参数"的终极形态：有些参数连编译都不用重来，直接在成品上"改字节"。

### 6.3 技巧三：缓存工具链参数 + 并行编译链接

- 第一次用 `pio run -e moj -v` 提取工具链路径和完整命令行，**缓存**起来
  （`platformio.ini` 没改就复用），之后脚本直接调 `g++` 自己编，跳过 pio 的开销。
- 所有 `.o` 用线程池并行编译（`ThreadPoolExecutor`）；链接也并发但有上限
  （避免内存爆掉）。
- 用源码指纹（`_src_fingerprint`）判断缓存是否过期：新增/改了源文件就自动失效重提。

### 6.4 为什么"结合不出错"——隔离是关键

TPU 专用固件（设 `BMCU_TPU_MODEL` 时）输出到**独立目录** `firmwares-tpu/`，
与常规 `firmwares/` 完全隔离；它的变体 `.o` 用独立的 `tpu_vkey` 命名空间，
**不污染**常规构建的数据结构。常规全量构建"零差异"。

每个固件的 `.o` 组合由 `build_link_objs(vkey, ...)` 按 `vkey`
（模式组合的唯一键）精确挑选并链接，顺序完全复刻 pio 原始链接命令
（从 `-v` 输出动态解析），所以不会出现"链接顺序错导致 undefined reference"。

## 7. 设计这套系统要考虑什么（给想深入的人）

如果你将来要维护或扩展这类"一源码多固件"的项目，重点考虑这几条：

1. **开关的边界要干净**：每个 `#ifdef` 包裹的代码块，必须保证"定义了"和
   "没定义"两种情况下都**语法完整、能独立编译**。之前 `Acol` 的坑就是反例。
2. **能写死就写死，能运行时查就运行时查**：
   - 改变**行为逻辑**的 → 用 `#ifdef`（编译期裁切）；
   - 只改变**数值**的 → 优先写成可配置/可查表，避免为了一个数值重编整个文件
     （本项目用二进制修补是更极端的优化，普通项目用查表/Flash 配置更稳妥）。
3. **分类与缓存要可验证**：脚本靠"哪些宏影响哪些文件"来省编译。一旦新增源文件
   引用了某宏却没被分类到，就会用错 `.o`。本项目用源码指纹 + 占位符计数校验
   来兜底（见 `tpu_sentinel_counts` 检查）。
4. **输出隔离**：不同族固件放不同目录，避免命名冲突和互相覆盖。
5. **复刻原始构建链**：脚本没有自己造链接规则，而是从 pio 的 `-v` 输出里
   **抓真实的命令行**来用——这样最不容易出错。

---

## 8. 给纯小白的一句话总结

- **编译参数 `-Dxxx=1`** = 在编译前给源码里定义一个开关；
- 代码用 **`#ifdef`** 围绕开关写，开关关掉那段代码就"不存在"于成品里；
- 所以**同一份源码**，给不同开关组合，就裁出**不同、且互不干扰**的固件；
- 上千个固件能又快又准地编出来，靠的是：把"不受开关影响的代码只编一次" +
  "只改数值的用二进制直接改字节" + "并行编译 + 缓存"。

这就是嵌入式固件"一套代码，千种出厂"的标准玩法。
